# 后端审查整改设计

日期：2026-08-31

## 目标

在保持现有 FastAPI 路由和前端调用方式基本不变的前提下，修复本次后端审查发现的权限越界、成绩完整性、导入幂等和稳定性问题。

本次实现范围：

1. 普通用户只能查看个人排行数据；部门管理员只能查看本部门及子部门；超级管理员查看全局数据。
2. 排行统计只纳入已发布的正式考试成绩，不纳入模拟考试或未发布成绩。
3. 已发布/进行中的考试禁止修改影响作答和评分的核心规则，并冻结已引用题目的快照。
4. 每个考试会话保存自己的选项打乱映射，提交时还原答案后判分。
5. 严格拒绝空白或与选项不匹配的题目答案结构。
6. 预览 token 改为 SQLite 持久化、一次性原子消费，并绑定操作者和过期时间。
7. 增加请求大小、导入、限流、统计查询和异常处理方面的防护。

## 非目标

- 不迁移 PostgreSQL，不引入 Redis 作为强制依赖。
- 不重写前端页面和现有 API 路径。
- 不修改三个可选 Nit：默认 CORS 策略、初始化日志输出方式、缺少 JWT 密钥时的启动策略；这些作为后续运维改进单独处理。
- 不做与本次审查无关的全量代码风格重构。

## 设计原则

- 先写回归测试，再改生产代码。
- 业务权限在 service 层再次校验，路由层只做依赖注入和基础参数校验。
- 所有一次性动作使用数据库条件更新保证幂等。
- 预览数据和 token 的生命周期由数据库控制，不依赖单进程内存。
- 保持现有响应字段；新增字段只用于内部持久化或兼容性增强。

## 方案一：权限与统计

### 排行权限

`GET /api/rank` 保留现有路径和查询参数：

- 角色只从 `get_current_user()` 返回的数据库用户读取，绝不接受客户端 role 参数。
- `role=user`：只返回当前用户自己的统计；客户端传 `scope=group` 时强制按个人处理，不扩展到其他用户。
- `role=dept_admin`：只返回其 `dept_group_id` 子树内用户；分组排行也只聚合这些分组。
- `role=super_admin`：返回全量排行。

`stats_service.rank()` 增加调用者范围参数，优先使用 SQL 子查询过滤用户，避免把大批用户 ID 拉到 Python 后再拼 `IN`。

个人榜按用户唯一统计。分组榜在查询时 JOIN `UserGroup`；一个用户属于多个直接分组时会分别计入这些分组，只有 `dept_group_id`、没有 `UserGroup` 的用户计入其部门分组。部门管理员只聚合其子树内分组，未分组用户不进入分组榜。`StatsUserDaily.group_id` 保留兼容但不再作为分组榜的唯一归属来源。

### 成绩统计

`refresh_daily()` 聚合考试成绩时 JOIN `exam_definitions`，并限定：

```sql
exam_definitions.type = 'formal'
AND exam_results.published = 1
```

这样模拟考试和待复核/待公布成绩不会进入考试均分、考试次数和排行榜。

### 管理端概览

部门管理员的题目数、完成率、考试数、答题数、复核数和活跃数统一使用同一份 scope 规则。题目分母只统计 `Question.group_id` 在 scope 内的题目；完成率只统计范围内用户对这些题目的状态。考试范围采用“考试全部指派分组均在 scope 内”的口径，与考试列表、成绩列表保持一致。

## 方案二：考试完整性

### 状态机

本次不新增后台调度器，也不依赖状态字段自动变化。现有 `ExamDefinition.status` 保留兼容值，但规则判断以“是否为 draft + 时间窗口 + 会话状态”为准：

- `draft` 才允许修改题目来源、题目清单、时长、及格线、分组和评分开关。
- `published/ongoing/reviewing/ended` 只允许修改不影响历史成绩的展示名称（如确有需要），核心字段一律返回 409。
- `publish_exam` 只允许从 `draft` 原子变为 `published`；重复发布返回幂等成功或 409，统一采用 409。
- 已存在会话或成绩时，禁止重新发布或改变核心规则。
- 发布前必须验证题目引用、模板引用、时间格式、时间先后和试卷非空。

所有更新/发布使用带状态条件的 SQL UPDATE 并检查 rowcount。涉及规则发布、token 消费、复核/公布的竞争事务显式使用 `BEGIN IMMEDIATE`，配置 busy timeout，并进行有限次数整事务重试；仍失败时返回 503。时间窗口继续由 `_within_time_window()` 作为开考的最终判定，状态展示可通过统一的 `effective_status()` 派生，不要求每分钟写库。

### 题目快照

`ExamQuestion` 增加 `snapshot` JSON 字段，保存 `type/question/options/left_items/right_items/answer/analysis`。考试从 `draft` 发布为 `published` 的同一事务内完成题目固化和快照写入，快照不允许延迟到首次开考。会话展示和交卷判分只读取快照，不再读取可被管理员修改的 `Question` 当前内容。

分值的唯一数据源仍为 `ExamQuestion.score`；总分、客观题判分、简答复核和成绩公布都读取该列，`snapshot` 不重复保存 score。旧数据迁移时，如果快照为空，按当前题目回填；无法回填的考试阻断迁移并要求人工处理。

### 会话级选项打乱

在 `ExamSession` 增加 `shuffle_maps` JSON 字段，结构为：

```json
{
  "question_id": {
    "A": "C",
    "B": "A",
    "C": "B"
  }
}
```

开考时根据会话随机源为单选、多选题生成映射并保存；`session_payload()` 返回按映射重排后的选项，但仍使用前端现有 A/B/C 字母交互。交卷时使用反向映射把用户答案还原到快照答案坐标后调用 `grade()`。判断、填空、简答和拖拽题不改变现有语义。

`ExamQuestion.shuffle_map` 保留为旧字段，不再作为新逻辑的数据源；新逻辑唯一以 `ExamSession.shuffle_maps` 为准。新会话在创建会话的同一事务内生成并保存映射。旧的进行中会话若 `shuffle_maps` 为空，一律写入 identity 映射，保证已经保存的答案字母不会被重新解释；已经提交的会话不再修改。映射方向固定为“显示字母 -> 快照原始字母”，并校验为双射。

### 答案语法

- `None` 表示清除当前答案/未作答，允许保存。
- 单选：一个大写字母，必须落在当前显示选项范围内。
- 多选：一个或多个不重复大写字母，必须落在显示选项范围内，保存前排序。
- 判断：只能是“正确”或“错误”。
- 填空：1~100 个空；每个用户答案为最长 500 字符的字符串。题库参考答案每空包含 1~20 个非空等价答案。
- 简答：最长 20,000 字符。
- 拖拽：1~200 对；key/value 必须来自快照的左右题项，且同一题项只能使用一次。

非法结构统一返回 400，不写入 `ExamSession.answers`。发布考试前再次校验题目快照的 options/answer 一致性。

## 方案三：导入预览 token

### 数据模型

新增 `ImportPreview` 模型和表，字段：

- `id`
- `token_hash`：原 token 的 SHA-256，唯一索引
- `kind`：`question` 或 `user`
- `owner_id`：创建预览的管理员用户 ID
- `payload`：JSON 预览数据
- `created_at`
- `expires_at`
- `status`：`pending/succeeded`
- `consumed_at`：成功消费时间，可为空
- `result`：成功导入的统计结果，可为空

前端仍接收随机 `secrets.token_urlsafe(32)` 原 token；数据库只保存哈希。

### 用户导入密码

用户导入预览时立即对初始密码执行 bcrypt 哈希，token payload 只保存 `password_hash`，确认导入时不再保存或重新传输明文密码。

### 原子消费与失败恢复

预览创建时完成用户归属、题库/分组范围和 payload 格式校验。确认导入时，token 抢占和实际导入放在同一个数据库事务中：

```sql
UPDATE import_previews
SET status = 'succeeded', consumed_at = :now, result = :result
WHERE token_hash = :hash
  AND owner_id = :owner_id
  AND kind = :kind
  AND status = 'pending'
  AND expires_at > :now
```

实际实现使用 `BEGIN IMMEDIATE` 开启写事务，在同一事务中校验并导入数据，最后用上面的条件 UPDATE 标记 `succeeded` 后提交；任何异常都回滚 token 和导入数据，token 保持可重试。客户端在网络超时后再次提交时，只有相同 `owner_id + kind` 且状态为 `succeeded` 才返回已保存的 200 `result`；其他情况统一返回 400。并发请求只有一个能更新成功，另一个在提交后读取到同一 `succeeded` 结果。

外部错误统一为“预览不可用”（400），不区分不存在、过期、归属不符或 kind 不符；已成功消费的同 owner/kind 重试是上述唯一例外。详细原因只写内部日志。SQLite 锁冲突设置 busy timeout，超过重试次数返回 503。

增加过期记录清理函数，在预览创建和启动维护时执行；迁移脚本必须可重入，失败时保留原表并可回滚。

## 输入、稳定性和性能

1. JSON 请求体默认上限 1 MiB；考试答案上限 64 KiB；草稿 payload 上限 256 KiB；JSON 嵌套深度上限 8、单个集合元素上限 1000。上传接口继续使用现有独立文件上限。请求体在 JSON 解析前由反代/Uvicorn 和应用中间件共同限制。
2. Excel 只把“bytes -> 解析结果”的纯函数放入线程池；SQLAlchemy `Session` 不跨线程传递，数据库校验和写入在请求线程或线程内新建 Session 完成，并限制并发解析数。
3. 新增 SQLite `rate_limit_buckets` 表，使用原子 UPSERT 实现多 worker 共享的固定窗口计数；答题、草稿、标记接口增加用户级限流，现有认证/上传限流迁移到同一后端。桶按 `scope/key/window_start` 唯一，过期桶在请求和启动维护时清理。
4. 用户邮箱统一 `strip().lower()`，增加大小写不敏感唯一约束迁移；迁移前扫描冲突并停止，输出待人工处理的邮箱，不自动合并账号。
5. 用户分组 ID、考试题目 ID、模板 ID 在写入前显式验证，错误返回 400/403，不让外键异常变成 500。
6. 排行、统计和范围过滤改用 JOIN/子查询，减少 N+1 和超大 `IN` 列表。
7. `_streak()` 使用传入的日期范围。
8. 审计日志改为只 `add/flush`，由业务 service 统一提交；被审计的写操作与审计记录同一事务成功或回滚。所有管理端写路由传入经 `get_client_ip()` 解析后做 HMAC 的 IP 标识，不保存原始 IP；detail 只允许业务 ID、状态和字段名，过滤密码、token、邮箱和姓名。
9. `ExamResult.exam_session_id` 增加唯一索引；迁移前检查重复结果并阻断，防止重复计分。

### 复核与统计一致性

复核提交和成绩公布都要求 `ExamResult.published = false`。复核记录的条件 UPDATE 同时检查所属成绩未公布；公布操作在同一 `BEGIN IMMEDIATE` 写事务内重新统计待复核记录并更新成绩。已经公布的成绩不允许再复核或加分。

所有把 `published` 从 false 改为 true 的路径都必须在业务事务提交后刷新对应日期统计，包括 `submit_exam()` 立即公布和 `publish_results()` 人工公布。刷新使用新 Session 执行可重入的 `refresh_daily()`；刷新失败记录错误并由启动刷新/手动刷新兜底。

具体条件更新使用 `EXISTS` 子查询检查所属 `ExamResult.published = false`。SQLite 写事务会串行化复核和公布：先提交复核则公布看到新分数；先提交公布则后续复核 rowcount 为 0 并返回 409。

## 错误处理

- token 不存在、过期、归属不符或 kind 不符统一返回同一种 400，不泄露 token 状态或其他用户的 payload；同 owner/kind 的成功重试返回原成功结果。
- 已发布考试修改返回 409，避免被误认为参数错误。
- 非法题目答案、非法引用和时间配置返回 400。
- Excel 可预期解析异常统一转换为 400，并确保数据库事务回滚；未知程序异常保留 500，避免吞掉真实缺陷。
- 并发版本冲突继续返回现有 409 语义。

## 测试方案

新增或补充以下测试，全部先建立 RED 再实现：

1. 普通用户只能看到自己的排行；部门管理员看不到其他部门排行；超级管理员可看全量。
2. 未发布正式成绩和模拟成绩不会进入排行。
3. 部门概览所有指标都按 scope 过滤，混合分组考试口径一致。
4. 同一个导入 token 并发确认只有一次成功；不同用户不能消费；过期 token 不能消费。
5. 已发布/进行中的考试修改核心规则返回 409；草稿仍可修改。
6. 单选/多选会话选项打乱后，提交显示字母仍能正确判分。
7. 空白填空答案、空白拖拽映射和超出选项范围的答案被拒绝或判错。
8. 超大答案/草稿、非法分组 ID、非法 Excel 角色状态得到预期 4xx。
9. `_streak()` 在 7d/30d/all 范围内结果正确。
10. 上传解析在线程池执行，不阻塞事件循环的行为通过可测试的封装验证。
11. 复核与公布并发时不会给已公布成绩追加分数；公布后同日统计会刷新。
12. 旧库迁移、迁移重复执行、邮箱大小写冲突、重复 ExamResult、无法回填题目快照均有测试。
13. 独立进程模拟多 worker，验证 token 和限流计数共享。

现有测试、Ruff、MyPy 作为回归基线。开发依赖增加 `pytest-cov`，执行：

```bash
uv run pytest --cov=app --cov-report=term-missing --cov-fail-under=75
```

全项目覆盖率最低 75%，本次新增/修改核心模块目标 80%。

## 迁移与发布

本次 SQLite 发布采用停机维护，不做滚动部署：

1. 停止全部应用进程和写入，执行 checkpoint，并使用 SQLite backup API 生成一致性备份。
2. 运行可重入迁移脚本：先做邮箱/重复成绩/题目快照可回填检查；检查不通过则不修改 schema。
3. 检查通过后，在事务中创建 `ImportPreview`、`RateLimitBucket`，增加 `ExamSession.shuffle_maps`、`ExamQuestion.snapshot`，回填快照和旧进行中会话的 identity 映射，最后创建结果和邮箱唯一索引。
4. 迁移完成后部署只使用新 schema 的代码，不保留旧内存 token 双读逻辑。
5. 启动后运行完整测试和一次手动导入/开考/交卷冒烟；失败则停止服务并用 backup 恢复。
6. 不修改现有路由路径，前端只需兼容后端返回的重排选项。

## 验收标准

- 所有 Critical 回归测试通过。
- 现有测试全部通过。
- `ruff check`、`ruff format --check`、`mypy` 通过。
- 不再出现跨部门排行/概览数据、重复导入、已发布考试规则被覆盖或空答案得分。
- SQLite 旧库可完成迁移，单 worker 和多 worker 均可消费导入 token；邮箱、考试结果和题目快照冲突会被明确阻断，不会静默覆盖。
